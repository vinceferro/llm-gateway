# Clean-container install validation (C4) — 2026-08-30

Does the OSS claim "a stranger can install this from zero in a fresh
environment" hold? Three independent installs of `install.sh` inside fresh
Docker containers, each followed by a gateway start and HTTP verification. No
live providers, no paid APIs — the only network used is the public
`node:22-bookworm` base-image pull. All provider traffic in the verification
goes to the in-process mock provider.

## Result

| run | install.sh (s) | install→first HTTP 200 (s) | total (s) | pass |
|-----|---------------:|---------------------------:|----------:|------|
| 1   | 0.292          | 0.211                      | 0.504     | yes  |
| 2   | 0.296          | 0.213                      | 0.509     | yes  |
| 3   | 0.304          | 0.212                      | 0.516     | yes  |
| **mean** | **0.297** | **0.212**                  | **0.510** | 3/3  |

One-time base-image pull (excluded from the per-run numbers above): **24.6 s**.
All three runs exited 0 and answered every success-criteria probe on the first
attempt. No install.sh failures, no retries, no manual fixes.

## Method (copy-pasteable)

If your user is in the `docker` group but the group was added mid-session,
plain `docker` fails with permission denied — run each block through
`newgrp docker <<'EOF' … EOF` (what was done here). If `docker ps` already
works for you, drop the `newgrp` wrapper.

```bash
# 0) base image — pull once, timed separately (one-time cost)
docker pull node:22-bookworm
docker image inspect node:22-bookworm --format '{{join .RepoDigests ","}}'

# 1) payload = clean-clone equivalent: tracked files at HEAD, nothing else
git archive HEAD | tar -x -C /tmp/c4-payload   # creates the dir first
ls /tmp/c4-payload/install.sh /tmp/c4-payload/src /tmp/c4-payload/package.json

# 2) three independent runs; nothing carries over between them
for n in 1 2 3; do
  docker run -d --rm --name c4-run-$n node:22-bookworm sleep infinity
  docker exec c4-run-$n mkdir -p /payload
  docker cp /tmp/c4-payload/. c4-run-$n:/payload/
  docker exec c4-run-$n bash -c '
    T0=$(date +%s.%N); cd /payload
    bash install.sh >/tmp/install.log 2>&1; rc=$?; T1=$(date +%s.%N)
    cd /root/.llm-gateway/app
    nohup ./bin/gateway start >/tmp/gw.log 2>&1 &
    code=000
    for i in $(seq 1 150); do
      code=$(curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8090/healthz) && [ "$code" = 200 ] && break
      sleep 0.2
    done
    T2=$(date +%s.%N)
    echo "rc=$rc healthz=$code"
    awk -v a=$T0 -v b=$T1 -v c=$T2 "BEGIN{printf \"install=%.3f to_http=%.3f total=%.3f\n\", b-a, c-b, c-a}"
  '
  docker stop -t 2 c4-run-$n   # --rm removes it
done
```

Per-run timing is taken inside the container from one clock (`date +%s.%N`):
`install` = `install.sh` process wall time; `to_http` = install.sh exit →
first `GET /healthz` 200 (polled at 200 ms, so values carry up to +0.2 s
quantization); `total` = install start → first 200.

What a stranger would get, and what they would not: `git archive HEAD` contains
exactly the tracked files — `install.sh`, `src/`, `test/`, `bench/`, `bin/`,
`scripts/`, `package.json`, `package-lock.json`, docs, `config.example.json`
(sanity-checked before the runs). It naturally excludes `.git`, `node_modules`,
untracked machine-local files (`llm-gateway.json`, `*.bak-*`) and internal
working notes (`.kickoff/`, `.claude/`, `.opencode/`) — the public-mirror
export excludes those too. Timings were measured on this source tree; the
code in the public tree is identical, so the numbers describe the published
artifact as well.

## Environment

- Host: Linux, aarch64. Docker 29.7.2 (client = server), containerd image store.
- Image: `node:22-bookworm`, digest
  `sha256:8a34c4ab3ea2c5cd194f07e317b2a8f09461d3c8b05c4e34c8ccd56d56024c4d`
  (image created 2026-08-25). Size as observed: containerd content 416 MB /
  disk usage 1.63 GB / `inspect .Size` 399,652,651 B — the three commands
  account differently; all three are recorded as reported.
- Why bookworm and not alpine: `install.sh` is `#!/usr/bin/env bash` and
  alpine has no bash by default. bookworm also ships node ≥ 22.6, npm, curl —
  everything the preflight requires.

## Success criteria (all three runs)

1. `install.sh` exits 0.
2. Gateway starts via the installed launcher (`bin/gateway start`; no systemd
   in the container → correctly falls back to foreground).
3. `GET /healthz` returns 200 — keyless, no upstream, no key material needed.
4. `GET /v1/models` with the bootstrap-generated gateway key returns 200
   listing `mock-local`.
5. `POST /v1/chat/completions` with that key and `X-Task-Class: testing`
   returns 200 with content `"pong"` and `x-lg-provider: mock-local` — served
   by the in-process mock provider (`src/mock.ts`), zero external API calls —
   and appends one row to `~/.llm-gateway/usage.jsonl` (verified).

Why this is a fair proxy: with no local model server detected, the installer's
bootstrap writes a valid config routed to the mock provider, so the full HTTP
auth → routing → ledger path is exercised exactly as a fresh user would
experience it, minus a real upstream.

## What install.sh did in the container (from the captured full log)

- Preflight passed (node 22.x, npm, curl present in the image).
- Copied the checkout to `~/.llm-gateway/app` via tar (checkout path, not the
  git-clone path), then `npm install --omit=dev` → "up to date in 156ms"
  (zero runtime deps; no package fetches).
- `src/bootstrap.ts --detect` probed 127.0.0.1 ports, found nothing, wrote a
  valid mock-provider config + gateway key + admin key, config 0600.
- systemd step skipped cleanly (no systemd in container); env file written.

## Findings (nothing stranger-blocking; one papercut)

- **Shim PATH papercut.** In the container, `~/.local/bin` is not on PATH, so
  `install_shim` takes its note branch and does NOT create the `gateway`
  command — the finish panel then says `gateway start`, which fails with
  "command not found" until the user either adds `~/.local/bin` to PATH or
  uses the path install.sh itself prints (`/root/.llm-gateway/app/bin/gateway`).
  install.sh does print that actionable note immediately before the panel, so
  this is friction, not a blocker. On typical desktop setups
  (`~/.local/bin` on PATH) the shim installs and the panel is correct as
  written.
- Timings are far below any threshold that matters: sub-second install,
  sub-second to first successful response, on this image.

## Limitations

- One host, one architecture (aarch64), one image tag, one install.sh commit.
  x86_64 boxes and other node:22 digests are untested here.
- Base-image pull time (24.6 s) is reported separately, not in the per-run
  numbers; a stranger's real first-run experience includes it.
- This exercised install.sh's **checkout-copy path** (payload present in
  $PWD). The **curl-pipe path** (`git clone --depth 1` of
  `$LLM_GATEWAY_REPO_URL`) was NOT exercised — this run validates installer
  mechanics from a checkout; the curl-pipe path is proven only after
  publication, when a stranger can actually clone the public repo (run the
  curl-pipe install yourself and these numbers gain their final row).
- All traffic was mock-provider; no real provider (and no real key) was
  contacted, so this says nothing about funded-provider setup.
- Timings come from `date +%s.%N` on one machine with warm page cache; no
  dispersion statistic was computed (n=3).
- Throwaway in-container keys were generated by the installer and died with
  the containers; none were real, none were printed anywhere they matter.

## Falsification

The claim "quick install from zero works" would be disproven by any of:

- `install.sh` exiting non-zero, or requiring any manual step beyond
  "copy payload in, run it", in a fresh container from this image.
- The gateway failing to answer `/healthz` 200 within seconds of
  `gateway start` after a successful install.
- Any success-criteria route failing with the bootstrap-generated config
  (e.g. 401 with a freshly generated key, or a config the loader rejects).
- A materially different result on repeat (n=3 here): e.g. install time
  seconds-scale instead of sub-second, or flaky bootstrap. This document's
  numbers are claims about THIS image digest, host, and commit — re-run the
  method above to re-establish them elsewhere.
